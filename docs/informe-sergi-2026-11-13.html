2. El bloqueo principal: traducción y Azure

La clasificación puede funcionar con un proveedor local, pero la traducción sigue dependiendo de Azure Translator. El código actual usa ManagedIdentityCredential, que solo existe dentro de un recurso Azure con identidad administrada. En un Linux local no hay esa identidad.

Qué ocurre hoy

PiezaEstadoConsecuencia
Clasificación con LLM localDisponiblePuede probarse con Qwen o DeepSeek

Azure TranslatorSin acceso ni identidadBloquea la clasificación real

Riesgo si no se resuelve: la app puede arrancar y clasificar en inglés, pero una factura en español fallará en la traducción. No es un problema de código de negocio; es un problema de autenticación e infraestructura.

Las tres opciones

OpciónQué implicaRecomendación
A. Azure completoDesplegar en Azure con identidad administrada, Foundry y TranslatorLa más fiel al diseño actual; recomendada para producción
B. Translator con clave o service principalCambiar translation.py para aceptar una credencial de desarrolloÚtil para local; requiere una decisión de arquitectura
C. Traducción localAñadir un proveedor local de traducción con Qwen u otro modeloMás trabajo y riesgo de calidad; no mezclar con producción sin medir

La opción B o C debe aprobarla el owner. El diseño actual mantiene Translator como dependencia obligatoria y no incluye fallback silencioso.

4. Decisiones técnicas pendientes

4.1 Traducción

Es la decisión más importante. El código actual exige Azure Translator con identidad administrada. Para desarrollo local hay que elegir entre:

  • Mantener Azure Translator y probar dentro de Azure o con una credencial de desarrollo.
  • Añadir una credencial de service principal o clave solo para desarrollo, sin cambiar el comportamiento de producción.
  • Implementar traducción local, con un proveedor alternativo y una evaluación de calidad antes de usarlo.

Recomendación: no mezclar. Producción con Azure Translator e identidad administrada; desarrollo con una vía explícita y separada, aprobada por el owner.

4.2 Proveedor LLM

El proveedor se selecciona solo por entorno:

VariableValorUso
LLM_PROVIDERazure o localAzure por defecto; local opt-in
AZURE_AI_PROJECT_ENDPOINTEndpoint FoundryClasificación Azure
AZURE_AI_MODEL_DEPLOYMENTMAI-Thinking-1Deployment del modelo
AZURE_TRANSLATOR_ENDPOINTEndpoint TranslatorTraducción
LOCAL_LLM_BASE_URLURL localSolo si LLM_PROVIDER=local

No hay selector de proveedor en API ni en UI, y no debe haber fallback silencioso. Un error del proveedor elegido debe verse como error.

4.3 Qdrant y datos

Qdrant guarda el catálogo HS y los embeddings. En local se puede usar Docker; en Azure hay que decidir entre Qdrant gestionado, contenedor con almacenamiento persistente o una base vectorial equivalente. La decisión afecta a coste, backup y latencia.
